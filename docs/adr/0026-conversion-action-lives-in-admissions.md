# ADR-0026: Conversion Action Lives in Admissions, Not People

**Status:** Accepted

**Date:** 2026-07-27

## Context

Sprint 4.3's original approved specification placed `ConvertApplicantToStudentAction` in the People module, reasoning that "Admissions never writes Student/Enrollment tables directly" — an ownership argument about which module's tables get written, not about import direction. An independent read-only repository review, run after implementation, mechanically confirmed via `deptrac analyse` that this placement violates `deptrac.yaml`'s own layering ruleset: `People` is classified under `Foundation`, `Admissions`/`Academic` under `Domain`, and Foundation's ruleset entry (`Foundation: [Core, Foundation, Administration]`) deliberately excludes Domain — the same one-way-dependency discipline already documented for Administration and Domain elsewhere in that file. 11 violations were reported, all newly introduced by Sprint 4.3, zero pre-existing violations of this class anywhere else in the codebase.

The review presented three resolution options without picking one, per this project's standing rule that an architectural contradiction be surfaced and explicitly decided, not silently worked around: (A) move the Action and its exceptions into Admissions; (B) introduce a Core-level abstraction so People never imports Admissions' concrete `Applicant`; (C) reclassify People's layer in `deptrac.yaml`. The user reviewed all three and selected Option A.

A related, narrower question surfaced during that same review: `Enrollment` (which stays in People — its own placement was already settled by an earlier, separate decision in this sprint, and was not reopened) declares `academicYear()`/`gradeLevel()` `BelongsTo` relations directly against Academic's `AcademicYear`/`GradeLevel` models. Moving the Action does not fix this — it is Foundation depending on Domain regardless of which class does it. A grep across the full backend confirmed nothing consumes these two relations (not the Action, not any test), so removing them was zero-risk. The user confirmed removing both, keeping the underlying `academic_year_id`/`grade_level_id` FK columns as plain integers.

## Decision

1. **`ConvertApplicantToStudentAction` moves from `App\Modules\People\Actions` to `App\Modules\Admissions\Actions`.** Its three exceptions — `ApplicantNotAcceptedException`, `ApplicantAlreadyConvertedException`, `PaymentNotConfirmedException` — move from `App\Modules\People\Exceptions` to `App\Modules\Admissions\Exceptions` alongside it, since each is thrown by a check the Action performs on `Applicant`, matching the project's existing "the module performing the validation owns the exception" precedent (`ClosedAcademicYearException` living in Academic, called from Admissions) — this placement is now *more* consistent with that precedent than the original one was, not less.
2. **`Student` and `Enrollment` stay owned by People**, unchanged. Only the calling code's location moves. The dependency direction becomes Admissions (Domain) → People (Foundation) for `Student`/`Enrollment`, which `deptrac.yaml`'s Domain ruleset entry (`Domain: [Core, Foundation, Administration]`) explicitly permits.
3. **`Enrollment::academicYear()` and `Enrollment::gradeLevel()` are removed.** The `academic_year_id`/`grade_level_id` columns remain on the `enrollments` table, populated exactly as before — only the typed Eloquent relation methods and their `AcademicYear`/`GradeLevel` imports are gone. Any future code needing the actual `AcademicYear`/`GradeLevel` row for an Enrollment queries Academic's own models directly by ID, from Domain-side code (Admissions/Academic), never through a People-side relation method.
4. **`ConvertApplicantToStudentAction`'s dependency on `AcademicCatalogService` (Academic) is not a violation** under the current `deptrac.yaml` configuration: `Admissions` and `Academic` are both collected into the single `Domain` layer (one regex matching all nine Domain module names), so a dependency between them is intra-layer, not cross-layer — the same pattern already exists, unflagged, in Sprint 4.2's `SubmitApplicationAction`. This is recorded here as a known gap between `deptrac.yaml`'s own stated intent ("never a sibling Domain module directly," per its comments) and what its current collector granularity actually enforces — not something this ADR resolves, since narrowing the Domain collector into per-module layers is a separate, larger decision affecting every existing Domain-to-Domain dependency in the codebase, not just this one.
5. **`Applicant::convert()`'s `ApplicantConverted` dispatch is deferred via `DB::afterCommit()`**, matching `StudentEnrolled`/`StudentReactivated`'s existing discipline. The same review found `ApplicantConverted` was the only one of the three events this sprint touches that still dispatched synchronously while being called from inside `ConvertApplicantToStudentAction`'s open transaction — an inconsistency introduced within this same sprint, not carried over from Sprint 4.2. Fixed at its declaration point in `Applicant::convert()` (not by requiring every future caller to remember `afterCommit()` externally), so it behaves correctly whether `convert()` is called standalone (fires immediately, no open transaction) or from within a wrapping transaction — the same pattern `Student::reactivate()` already uses.

## Consequences

Every future Domain module that needs to trigger a People-owned write (Student/Enrollment or any future People aggregate) now has a clear precedent: the calling Action lives in the Domain module that owns the business trigger, not in the Foundation module that owns the data — Foundation is written to, never the caller. `deptrac analyse` must be run as part of every sprint's verification going forward (see the Lessons Learned entry added to `IMPLEMENTATION_PLAYBOOK.md`) — it already was a documented Quality Gate requirement before this sprint (`IMPLEMENTATION_PLAYBOOK.md`'s "Quality gates" checklist, `deptrac — zero module-boundary violations`), but was not actually run during Sprint 4.3's own verification pass, which is how Finding 1 reached an independent review undetected instead of being caught during implementation.

The `deptrac.yaml` Domain-collapse gap (point 4 above) remains open — Admissions and Academic (and every other Domain module) can depend on each other freely today with no mechanical check, despite the file's own comments describing that as forbidden. This is recorded as a known limitation, not fixed here.

## Alternatives Considered

- **Option B — Core-level abstraction.** Rejected for now, not permanently: would require moving `Billable` from `Admissions\Contracts` to `Core\Contracts` (an interface still carries its declaring module's `deptrac` layer) and introducing a Core-level Applicant-shaped contract/DTO People could depend on instead of the concrete `Applicant` class. Heavier than Option A for a single current consumer; worth revisiting if a second Foundation module ever needs to trigger a Domain-originated action against People data, per this project's own promotion-not-prediction discipline (`docs/DOMAIN_BLUEPRINT.md` Addendum B1).
- **Option C — Reclassify People's `deptrac.yaml` layer.** Rejected — would change the layering contract for every other existing Foundation consumer of People (Identity, Media, IdentityMaintenance, Notifications), a much larger blast radius than this sprint's own scope, for no benefit beyond accommodating one new Action.
- **Leaving `Enrollment::academicYear()`/`gradeLevel()` in place, exempting them via some form of `deptrac.yaml` allowlist.** Rejected — `deptrac.yaml` has no per-class exemption mechanism consistent with this codebase's existing usage, and the relations were unused, making removal strictly simpler than carving out an exception.
