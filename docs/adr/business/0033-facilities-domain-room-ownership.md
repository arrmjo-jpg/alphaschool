# BUS-0033: `Room` Ownership — `Facilities` Introduced as a New Domain

**Status:** 🟢 Accepted

**Date:** 2026-07-28 (revised same day — first draft was 🟡 Proposed pending review; Accepted after the user's DDD/boundary review added the Non-Goals section and hardened the consumption rule to a named-contract-only requirement)

**Related Domains:** Academic (consumer, first), Facilities (new domain, this ADR's subject), Inventory (adjacent, explicitly distinguished), Smart Campus & Physical Security (future consumer, controls a Room's environment/access but does not own its registry), School Operations & Campus Automation (potential future consumer)

**Related ADRs:** BUS-0018 (Subject Offering's formula names Room as an axis — `Subject × Term × Section × Teacher × Room × Schedule` — without ever resolving its ownership); BUS-0032 (Term — the immediately preceding case of the same underlying pattern: an undefined axis in an already-Accepted formula, resolved via its own dedicated ADR before implementation continued)

## Context

The Subject Offering + Timetables Architecture Pass (Phase 5, Sprint C precursor) reached the same kind of gap BUS-0032 resolved for "Term": BUS-0018's own Accepted formula for Subject Offering names **Room** as one of its six axes, but no document anywhere — not `academic.md`, not any `docs/adr/business/*.md`, not `docs/BUSINESS_BLUEPRINT.md`'s Domain Map or Dependency Map — ever assigns Room's ownership, lifecycle, or shape. Unlike Term, this gap was caught and explicitly flagged by the user before any implementation touched it, with a binding instruction: Room may not be created inside Academic ("لا أسمح بإنشائه داخل Academic"), because Room will be consumed by domains with nothing to do with Academic — Exams, Labs, Booking, Events, and Smart Campus — making its ownership an institutional decision, not a Timetable-specific one. This ADR is the dedicated, independent decision that instruction required, produced before any Timetable code is written, per `docs/IMPLEMENTATION_PLAYBOOK.md`'s own recorded next-step note (lines 658, 693).

A read-only research pass across the existing documentation (this ADR's own preparation) confirmed the gap is real and found no existing domain that fits Room's shape.

## Problem

Which domain owns the canonical `Room` entity — the physical, bookable/schedulable space (classroom, lab, exam hall, meeting room, event venue) that Timetables, Exams, Labs, Booking, Events, and Smart Campus all need to reference — and, at the ownership-decision level only, what is that entity's rough shape and scope boundary relative to adjacent future domains?

## Alternatives Considered

- **Room inside Academic.** Rejected by explicit, binding user instruction, and independently unsound on the merits: Room will be consumed by Exams, Labs, Booking, Events, and Smart Campus — none of which are Academic concerns — so modeling it inside Academic would manufacture exactly the kind of false domain ownership `deptrac`'s layering discipline exists to prevent (a Domain module claiming a concept that isn't actually its own).
- **Room inside Inventory.** Rejected. `inventory.md:9` states explicitly: "this is not an OT domain — it issues no commands to physical hardware and has no life-safety dimension," and its entire lifecycle model (`docs/business-domains/inventory.md`'s classification algorithm) is built around issue/return/consume for movable, custodial, or consumable goods (Student Inventory, Custody Inventory, Consumable Inventory). A Room is never issued to or returned by a person, and multiple domains schedule against it concurrently — the opposite shape of everything Inventory's classification test is designed to sort. Room already appears once in `inventory.md:78` as a **Stock Location** value ("Warehouse, Room, Shelf, Bin") — but that is Room as a place inventory happens to sit, not Room as the bookable resource Timetables needs. Reusing that reference would conflate two unrelated concepts under one column.
- **Room inside Smart Campus & Physical Security.** Rejected. `smart-campus.md`'s entire domain premise is Operational Technology with command-priority/preemption and life-safety obligations (per CLAUDE.md's own standing rule, concretely realized there — e.g. Emergency structurally preempting Manual Override). Its "Smart Classroom" submodule *controls* a room's environment and access (temperature, locks, cameras) but never claims to own the canonical Room registry itself. Folding "which rooms exist, their capacity/type" — a mundane reference-data concern — into a domain whose whole identity is safety-critical command routing would blur that identity and force an unrelated class of change through a heavyweight command-priority design lens it doesn't need.
- **A single combined "Facilities & Assets" domain.** Rejected, at least for now. `docs/BUSINESS_BLUEPRINT.md`'s own Dependency Map (line 125) already records Inventory feeding "Assets (future, cross-reference not merge)" — existing guidance that Assets is meant to stay its own concept, cross-referenced rather than absorbed into whatever ends up owning physical space. Room (a fixed, concurrently-bookable space) and Assets (trackable, typically movable institutional equipment/machinery) differ enough in lifecycle and consumer set that merging them now would be the same premature scope-bundling this Blueprint has already rejected elsewhere (e.g. Billing Policies explicitly kept as several small, properly-typed entities rather than one generic table).
- **A new, narrowly-scoped `Facilities` domain, Room as its first entity.** Accepted — see Final Decision.

## Final Decision

1. A new Domain module, **`Facilities`**, is introduced — reusing the exact placeholder name already present in `docs/BUSINESS_BLUEPRINT.md`'s Domain Map ("Remaining, not yet documented" list, line 102), rather than inventing a new name for the same slot.
2. Facilities' first Master Data entity is **`Room`** — a physical, bookable/schedulable space. This ADR resolves ownership and rough scope only; `Room`'s actual fields/migration/model shape are deliberately **not designed here**, mirroring how BUS-0032 first resolved "what is Term" before a later, dedicated pass designed `SubjectOffering` around it.
3. Facilities is scoped to physical, bookable space only. **`Assets` (equipment/machinery) remains a separate, not-yet-designed future domain**, per the existing Dependency Map guidance cited above (Inventory → Assets, "cross-reference not merge") — this ADR does not fold Assets into Facilities.
4. Facilities is consumed by Academic (Timetables, and by extension Subject Offering's own `Room` axis) **only** through a public service contract — a future `RoomCatalogService` (or equivalently named class, exact shape decided in Facilities' own future Architecture Pass, not here), exposing read-only query methods in the same spirit as `AcademicCatalogService`'s own boundary (e.g. `find()`, `exists()`, `capacity()`, `isAvailable()`). Consuming code must never hold a typed relation or direct Eloquent reference to `Facilities\Models\Room` — `Academic -> Facilities\Models\Room` is explicitly disallowed, `Academic -> Facilities\Contracts\RoomCatalogService` (or its eventual real name) is the only legal path. This is stricter than `AcademicCatalogService`'s own precedent by explicit user instruction: not just "the conventional way to consume it," but a hard rule for this specific boundary. It will later be consumed the same way by Exams, Labs, Booking, and Events (all currently unscheduled), and by Smart Campus's Smart Classroom submodule (which controls a Room's environment/access but does not own its registry).
5. **Facilities' actual implementation is Designed, Not Yet Scheduled** — this ADR is a decision-only pass. Real migration/model/schema design happens in a dedicated Facilities Architecture Pass, timed whenever Timetables is actually ready to consume it, matching Administration Platform/Notification Engine/Communications' own precedent in `docs/IMPLEMENTATION_PLAYBOOK.md`'s "Designed, Not Yet Scheduled" table and BUS-0032's own Term-before-SubjectOffering sequencing.
6. Cross-module dependency direction: Academic (and later Exams/Labs/Booking/Events) → Facilities is Domain-to-Domain. `deptrac.yaml`'s current Domain collector does not mechanically check Domain-to-Domain boundaries at all (ADR-0026's own disclosed gap) — this dependency is convention-enforced only, same as every other Domain-to-Domain reference in this codebase today, not a new or special exception.

## Non-Goals

Stated explicitly, as its own section, precisely to prevent scope creep as the platform grows around Facilities — a future contributor must be able to answer "does this belong in Facilities?" from this list alone, without re-deriving the boundary from first principles.

**Facilities does not own:**
- Timetables / Academic Scheduling (Academic's own concern — Facilities answers "does this Room exist and can it be booked," never "what is scheduled into it")
- Room Reservations / booking transactions (a future Booking domain's concern, once scheduled — Facilities is Master Data, not a booking ledger)
- Physical Security, access control, cameras (Smart Campus & Physical Security's concern)
- Environmental controls — HVAC, sensors, occupancy monitoring (Smart Campus's concern)
- **Assets** — projectors, computers, interactive boards, 3D printers, microscopes, generators, vehicles, printers, furniture, or any other movable/trackable equipment. These are categorically different from a Room: they are acquired, assigned, depreciate, need maintenance schedules and warranties, and move between locations — a Room does none of these things. Assets is its own future domain (`Asset`, `Asset Category`, `Assignment`, `Warranty`, `Maintenance`, `Lifecycle`), explicitly out of scope here, consistent with the Blueprint's own existing "Inventory → Assets, cross-reference not merge" guidance. Folding Assets into Facilities now — just because both are "things the institution owns, not students" — would build a heterogeneous domain mixing a fixed-space registry with a fundamentally different acquire/depreciate/maintain lifecycle, exactly the God-Object risk this Blueprint has already rejected elsewhere.
- Inventory's own consumable/custodial goods (Stock, Consumables, Issue, Return, Disposal) — a fully separate lifecycle, already Inventory's own domain.

**Facilities owns only Physical Space Master Data** — in its own future Architecture Pass, expected to eventually cover `Building`, `Floor`, `Wing`, `Room`, `Room Type`, `Capacity`, `Accessibility`, `Reservation Policies` (the *policy* — e.g. "labs require instructor sign-off" — not the reservation transaction itself), and `Maintenance Status` (a simple state flag on the space, not the Maintenance domain's own future work-order lifecycle). None of this is designed here — this ADR fixes the domain boundary, not the schema.

## Why This Decision Was Chosen

Every rejected alternative is a domain whose own already-written self-description structurally excludes Room: Inventory explicitly disclaims being an OT domain and models a fundamentally different (issue/return/consume) lifecycle; Smart Campus's whole reason to exist is safety-critical command control, not mundane reference-data ownership; Academic is foreclosed by explicit, binding instruction, and independently wrong on the merits since Room's real consumer set (Exams, Labs, Booking, Events, Smart Campus) has nothing to do with Academic. A new, narrowly-scoped Facilities domain is the only option that doesn't force Room into a domain whose own stated identity contradicts what Room actually is. Reusing the Blueprint's own already-named "Facilities" placeholder — rather than inventing "Space" or "Room Registry" — avoids adding yet another undocumented future-domain name to an already-long "remaining, not yet documented" list, and keeping Assets separate matches guidance this Blueprint already recorded independently of this decision.

## Consequences

**Easier:** Timetables' own future architecture pass can proceed once this ADR is Accepted, referencing a real, owned `Room` concept rather than a placeholder axis in BUS-0018's formula. Exams, Labs, Booking, and Events all inherit one canonical Room registry to design against later, instead of each domain risking its own local reinvention.

**Harder / constrained:** Facilities is now one more Domain module every Room-consuming feature must integrate with through a public service contract, not a direct table read — the same discipline `AcademicCatalogService` already established, applied to a second Domain-owned resource. `deptrac.yaml`'s Domain collector regex will need a `Facilities` entry once real code exists (not yet — this ADR is decision-only). The Domain-to-Domain collapse gap (ADR-0026's disclosed limitation) now also covers Academic→Facilities specifically, alongside every other Domain-to-Domain reference already unchecked today.

## Future Implications

Establishes Facilities as the platform-wide canonical owner of physical, bookable space — not an Academic-specific concept, and not merged with Assets. Every future OT/booking-adjacent domain (Exams, Labs, Booking, Events, Smart Campus's Smart Classroom submodule) must reference Facilities' `Room`, never define a local room concept of its own. Unblocks the Timetables Architecture Pass named in the Phase 5 dependency analysis, now that this ADR is 🟢 Accepted.
